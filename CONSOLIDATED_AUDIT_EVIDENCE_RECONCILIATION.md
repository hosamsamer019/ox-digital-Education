### Discrepancy 4: Stored Language Preferences vs Live Multi-User Browser Isolation
* **Original Claim:** Storing language preferences in the database guarantees isolated user experiences.
* **Verified Reality:** Database persistence is confirmed, but **client-side browser isolation has active edge-case vulnerabilities**.
* **Evidence:**
  - PostgreSQL Dev DB (`ox_digital_dev_test` port 5433): all 7 active user accounts have persisted `language` values (`en` or `ar`).
  - `apps/frontend/src/app/contexts/LanguageContext.tsx`:
    - `applyUserPreferences`:
      ```typescript
      if (!userPreferences.language) return;
      ```
      If a user record has `language: null`, the function aborts early, leaving whatever preference was previously stored in the browser's `localStorage`.
    - `t()` fallback:
      ```typescript
      return translations[language]?.[key] || translations['ar']?.[key] || key;
      ```
      If an English dictionary key is missing, the application silently renders the Arabic string even when English is active.
  - Multi-session concurrency cannot be validated on a live browser until the updated container is deployed.
* **Classification:** **VERIFIED AT SOURCE LEVEL ONLY — BROWSER CONCURRENCY UNVERIFIED**
